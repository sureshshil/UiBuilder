## What this is

A single-page Next.js App Router app: an AI chat panel on the left generates a React/Tailwind component from a text prompt, and the right panel live-renders it in an in-browser Sandpack sandbox (with a raw-code/file-explorer view as an alternate tab). Users can upload a CSV/JSON/TSV file to get UI suggestions and bind real data into a generated component, save projects to Supabase, and one-click deploy the current sandbox to Vercel as a standalone Vite app.

Nearly the entire client UI lives in one file: [src/app/page.tsx](src/app/page.tsx).

## Commands

- `npm run dev` — start the dev server (http://localhost:3000)
- `npm run build` / `npm run start` — production build / serve
- `npm run lint` — ESLint (flat config, `eslint-config-next`)

There is no test framework (no Jest/Vitest/Playwright config). Correctness is checked with ad-hoc Node scripts that hit a **running dev server**: `node e2e-test.mjs`, `node simulate-e2e.mjs`, `node debug-flow.mjs`, `node test-bind.js`, `node test_error_regex.js`. Start `npm run dev` first, then run the relevant script directly with `node`.

## Architecture

### The AI generation contract

All three AI routes under [src/app/api/](src/app/api/) call Gemini via `@ai-sdk/google-vertex` (Vertex AI, not a direct Gemini API key — auth is via ambient Google Cloud credentials plus `GOOGLE_CLOUD_PROJECT`/`GOOGLE_VERTEX_PROJECT` and `GOOGLE_VERTEX_LOCATION`):

- **`/api/chat`** ([route.ts](src/app/api/chat/route.ts)) — the main generation/edit endpoint. Its system prompt is the single source of truth for the output contract: the model must return files as `<file path="/App.tsx">...</file>` XML-style blocks (no markdown fences, no `package.json`/vite/tailwind config files — those are fixed), and it documents every library available inside the sandbox (lucide-react, recharts, framer-motion, react-router-dom's `MemoryRouter`, react-hook-form+zod, Radix primitives, date-fns, etc.), plus hard rules like avoiding TDZ errors and tagging bindable components with `/* @bindable */` above their props interface.
- **`/api/bind`** ([route.ts](src/app/api/bind/route.ts)) — given the user's instruction, the `@bindable` contracts extracted from current code, and an uploaded data schema, generates *only* a new adapter/wrapper component that maps the data into an existing component's props, without touching the original component file.
- **`/api/suggest`** ([route.ts](src/app/api/suggest/route.ts)) — uses `generateObject` (structured output, zod schema) to propose 3 UI ideas for an uploaded data file.

**Any library list you add to the `/api/chat` system prompt must be mirrored in two other places**, or generated code will fail to resolve at runtime/deploy time:
1. The Sandpack `customSetup.dependencies` map in [page.tsx](src/app/page.tsx) (live preview).
2. The `vercelFiles` scaffolded `package.json` in [/api/deploy/route.ts](src/app/api/deploy/route.ts) (real deploy — note this pipeline uses Vite + Tailwind v3 configs, a *different* build setup than the Sandpack preview, so keep both dependency lists in sync manually).

### Client-side flow

- [src/services/copilotService.ts](src/services/copilotService.ts) is the only client for the three API routes. It also owns `extractBindableContracts`, a hand-written line-scanner (not an AST) that finds `/* @bindable */`-tagged interface+component pairs in the current generated code so the UI can offer a "bind data" suggestion.
- [page.tsx](src/app/page.tsx) parses the model's `<file path="...">` blocks with a regex into a Sandpack file map and renders it via `@codesandbox/sandpack-react` (`template="react-ts"`, Tailwind loaded via CDN in the sandbox, not a real Tailwind build).
- **Auto-heal loop**: [SandpackErrorListener.tsx](src/components/SandpackErrorListener.tsx) listens to both Sandpack's compile-error state and the preview iframe's runtime error channel, and reports errors up to `handleAutoHeal` in `page.tsx`, which re-prompts the model with the error text for up to 3 attempts before reverting to the last known-working code.
- Uploaded CSV/JSON/TSV files are placed in the sandbox's `/public/` dir; generated code is instructed to `fetch()` them at runtime rather than import/hardcode the data.

### Persistence

- [src/lib/supabase/client.ts](src/lib/supabase/client.ts) is a browser-only Supabase client. [Sidebar.tsx](src/components/Sidebar.tsx) handles email/password auth and lists/loads a user's saved projects.
- [schema.sql](schema.sql) defines the `projects` table with RLS policies scoped to `auth.uid() = user_id`.
- Saved project code has the chat history embedded as a base64 comment header (`CHAT_HISTORY_BASE64`) that `page.tsx` strips out again on load. Loading a project whose saved code starts with `{`/`[` (old pre-TSX-migration JSON format) is detected and rejected with a message asking the user to re-describe the UI instead of trying to parse it.

### Dead/unwired code — don't assume these are active

[src/lib/intentRouter.ts](src/lib/intentRouter.ts) and [src/lib/codeSections.ts](src/lib/codeSections.ts) implement a token-saving scheme that would split generated code into `// @@logic` / `// @@styles` / `// @@jsx` sections and send only the section relevant to the user's edit request, keyed off keyword matching. [src/lib/schema.js](src/lib/schema.js) is a compiled zod schema for a structured UI-tree format. None of these three files are imported from anywhere in the app — `copilotService.ts` always sends the full current code on every request. Treat them as an unfinished/abandoned optimization, not existing behavior.

### Required environment variables (`.env.local`)

`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `VERCEL_API_TOKEN` — plus ambient Google Cloud auth (`GOOGLE_CLOUD_PROJECT`/`GOOGLE_VERTEX_PROJECT`, optionally `GOOGLE_VERTEX_LOCATION`) for Vertex AI, which is not set via `.env.local` in this repo.
